## 项目简介
在分布式系统中，生产者和消费者往往不在同一台机器上，本地的阻塞队列已经不够用了。
### 背景
阻塞队列（BlockingQueue）最典型的用途就是实现生产者消费者模型。这个模型之所以在后端开发里无处不在，是因为它同时解决了几个现实问题：
- **解耦合**：生产者只负责把任务丢进队列，不需要知道消费者是谁、有几个、什么时候处理
- **支持并发**：生产和消费可以并行推进，不会互相阻塞
- **支持忙闲不均**：生产者速度快、消费者慢时，队列先把数据缓冲住
- **削峰填谷**：突发流量先入队，后端按自己的处理能力匀速消费
但一旦生产和消费跨越了机器边界，本地队列就无能为力了——不同进程、不同主机之间没法共享一块内存。业界的做法是把阻塞队列抽出来，做成一个独立的服务程序，并赋予它更丰富的功能：持久化、路由、确认重投、多客户端接入。这就是**消息队列（Message Queue）**。
成熟的产品有 RabbitMQ、Kafka、RocketMQ、ActiveMQ 等，其中 RabbitMQ 基于 AMQP 模型，概念清晰、功能完整，非常适合作为学习对象。
### 本项目做了什么
本项目仿照 RabbitMQ 的 AMQP 模型，实现了一个简化版的消息队列，包含**服务端（Broker）**与**客户端**两大部分，覆盖了从连接建立、协议交互、消息路由、投递确认到数据持久化的完整链路。
核心能力包括：
- **交换机、队列与绑定**：支持交换机的声明与删除、队列的声明与删除、队列与交换机之间的绑定与解绑，发布消息时按 `binding_key` 完成路由匹配
- **发布与订阅**：发布客户端投递消息，订阅客户端按队列订阅并接收服务端推送
- **消息确认**：消费者处理完成后回送确认；未确认的消息进入待确认队列，超时未确认则重新投递，避免消息在传输过程中丢失
- **持久化**：交换机、队列、绑定关系保存在 SQLite 中，消息体写入磁盘文件，进程重启后拓扑关系与未消费消息都能恢复
- **长连接与多客户端**：基于 muduo 的 epoll 事件驱动模型，支持多个客户端并发接入，一条连接上可承载多个信道
- **二进制协议**：应用层协议使用 protobuf 序列化，相比文本协议体积更小、解析更快，新增字段时也能保持向后兼容
## 技术栈
| 分类 | 选型 | 说明 |
|---|---|---|
| 开发语言 | `C++11` | 面向对象设计，配合 RAII、智能指针管理资源 |
| 网络库 | `muduo` | Leaded-Threaded Reactor 模型 |
| 序列化 | `Protobuf` | 二进制序列化 |
| 数据库 | `SQLite3` | 轻量级嵌入式数据库 |
| 构建工具 | `Makefile` | 组织多目录编译 |
| 单元测试 | `gtest` | 核心模块单元测试 |

几个选型的考虑：
- **为什么用 muduo 而不是原生 socket**：原生 socket 需要自己处理 IO 多路复用、连接生命周期、缓冲区管理，容易写出难以维护的代码；muduo 把这些问题封装好，可以专注在业务逻辑上，同时也便于理解 Reactor 模型的设计。
- **为什么用 protobuf 而不是 JSON**：消息队列对吞吐敏感，protobuf 序列化后体积通常是 JSON 的三分之一到十分之一，解析速度也更快，而且通过字段编号天然支持协议演进。
- **为什么用 SQLite 而不是 MySQL**：这个项目是单机组件，不需要独立的数据库服务；SQLite 以库的形式链接进程序，部署简单，同时支持事务与索引，足够保存元数据。
- **为什么用 Makefile 而不是 CMake**：项目目录结构固定、依赖不多，Makefile 足够表达编译规则，也便于直接看到每个源文件的编译与链接过程。

## 项目总结
### 完成了什么
本项目完整打通了一条消息从发布到消费的链路：客户端与 Broker 建立 TCP 长连接，在连接上打开信道（Channel），所有操作都在信道内发起；服务端在虚拟主机（VirtualHost）中完成交换机与队列的路由匹配，消息进入队列的内存管理结构并根据持久化标志决定是否落盘；订阅该队列的消费者收到推送后回送确认，消息最终从待确认队列中移除。
目前实现的功能覆盖了 RabbitMQ 最核心的那部分抽象：虚拟主机、交换机、队列、绑定、发布、订阅、确认，以及元数据与消息体的持久化。
### 技术收获
**1. 理解了 AMQP 模型为什么这样设计。**
一开始会觉得"交换机"是多余的抽象——直接把消息丢进队列不就行了？实际做下来才明白，交换机、绑定、路由键这套设计是为了把"消息往哪投"和"消息由谁消费"彻底解耦：发布方只需要关心往哪个交换机发、带什么路由键，完全不需要知道下游有多少队列、多少个消费者。这种解耦正是消息队列能在分布式系统里承担"中间层"角色的原因。
**2. 掌握了 Reactor 与 epoll 的实际用法。**
基于 muduo 实现网络层后，才真正理解"单线程处理网络 IO + 线程池处理业务"这套结构的意义：为每个连接创建线程的模型在几百连接时就会因为上下文切换而性能骤降，而 epoll 只在事件就绪时才唤醒处理逻辑，开销与连接数无关。
**3. 体会到持久化的复杂。**
消息既要在内存里高效流转，又要能落盘恢复，还要处理确认超时与重投，状态管理比预想的琐碎得多。比如一条消息可能同时处于"已投递未确认"和"已持久化"两个状态，进程崩溃后必须能根据磁盘记录判断哪些消息需要重新投递，这需要把内存状态和磁盘记录严格对齐。
**4. 认识到单元测试的价值。**
协议解析、路由匹配这类逻辑改动频繁，一旦出错往往表现为"消息莫名其妙丢了"或"投递到了错误的队列"，靠打印日志排查非常低效。用 gtest 把这些逻辑固化下来之后，改动前先跑一遍，能省下大量时间。
### 不足与改进方向
- 目前只支持基础的路由匹配，没有实现 topic 类型的通配符路由
- 没有做消息 TTL 与死信队列，消费失败的消息缺少兜底处理
- 缺少管理端，无法直观查看队列深度、连接数与消费速率
- 只支持单机部署，没有集群与数据同步
- 没有做压测，吞吐量与延迟缺少量化数据
这些是后续可以继续完善的方向，也是这个项目从"能跑通"到"能实用"之间还差的部分。
